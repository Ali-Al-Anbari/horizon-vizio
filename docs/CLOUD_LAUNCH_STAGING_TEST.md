# First paired-device cloud launch: staging plan

## Current state

The physical Vizio paired successfully with `horizon-pairing-staging` and retained its first-party session after leaving Conjure for Vizio Home and relaunching Horizon. With separate owner approval, the integrated staging Worker was deployed as version `40e435a0-db5b-4257-90cd-d1c6303f22fd`. It has `PAIRING_ONLY=false` and `STAGING_YOUTUBE_ONLY=true`. A separately approved cloud launch opened native YouTube on the physical TV; the Mac controller was stopped immediately afterward. Production Horizon has not been changed.

The review-only [launch configuration](../wrangler.pairing-staging-launch.jsonc) uses the **same Worker name, Durable Object class, binding, and migration tag** as the current [pairing-only configuration](../wrangler.pairing-staging.jsonc). It therefore uses the existing `primary-tv` Durable Object and its `device_pairing_v1` state. The command queue uses a separate `command_queue_v1` key in that object. The launch configuration sets `PAIRING_ONLY=false` and `STAGING_YOUTUBE_ONLY=true`; the five verified native mappings in the Mac controller remain unchanged. Other app tiles return `staging_app_disabled` at the Worker.

The Mac has a newly generated staging-only controller credential in a private mode-0600 file outside the repository. It was uploaded as a Worker secret without printing its value. An intentionally invalid authenticated result request returned JSON `invalid_result` with HTTP 400, confirming the credential reached Worker validation without claiming work or changing the TV. The SmartCast token remains in its existing private Mac file. No credential value belongs in Wrangler config, frontend assets, logs, URLs, or this document.

The first harmless controller probe received Cloudflare edge error 1010 before the Worker because Python's default HTTP client signature was blocked. An explicit `HorizonController/1.0` User-Agent then reached the Worker; that verified header is now part of the Mac controller. The check did **not** disable Cloudflare Browser Integrity Check or relax Worker authentication. See [Cloudflare's error 1010 explanation](https://developers.cloudflare.com/support/troubleshooting/http-status-codes/cloudflare-1xxx-errors/error-1010/).

## Security and queue checks

- Launch requires a valid first-party paired-device cookie; the Worker verifies its hash and the Durable Object rechecks it atomically with queue insertion. Unpaired, expired, or revoked sessions fail. An owner revocation cancels a command that has not yet been claimed. A command already claimed may already be reaching the TV.
- Browser writes require the exact same-origin `Origin` and a custom action header. The TV cookie is `Secure`, `HttpOnly`, `SameSite=Strict`, and scoped to the host. Other websites cannot use CORS or a public frontend value as authorization.
- Controller claim/result calls require a separate staging bearer secret. The controller itself accepts only the five verified app identifiers, and the first staging Worker deployment accepts only YouTube.
- One Durable Object holds one active command. A claim is atomic and one-time. Queued work expires after 30 seconds, claimed work after 35 seconds, results after 120 seconds, and a 12-second cooldown prevents immediate conflicting launches. A same-device duplicate receives the existing command ID; another device cannot read that command's status.
- A `verified` result means the Mac controller observed the expected authenticated `/app/current` state after the SmartCast request. An HTTP success from `/app/launch` alone is insufficient.
- The queue records `queuedAt`, `claimedAt`, `finishedAt`, and `elapsedMs` using its own clock. `elapsedMs` measures **enqueue to observed TV app state**, not the exact moment the image appears to the viewer. The Mac controller prints that duration without a token or command identifier. The owner's visual confirmation remains a separate check.

## Local verification completed

`npm run test:cloud` passes nine tests covering owner pairing, YouTube-only staging, missing controller configuration, unpaired/expired/revoked sessions, cross-site writes, unsupported apps, duplicate requests, atomic one-time claim, timeout, rotation, and measured result timestamps. `python3 -m unittest tests/cloud-controller-test.py` passes eight tests with mocked Cloudflare and SmartCast responses, including all five observed app-state mappings, accepted-but-unconfirmed TV launches, reconnect after a temporary network failure, and the explicit controller User-Agent. The launch Wrangler config passed `--dry-run`. These local mock and build results are separate from the physical-TV result below.

## Approved deployment and live YouTube result

1. The approved credential upload and `wrangler.pairing-staging-launch.jsonc` deployment are complete. Only the expected four secret names were present. Public Horizon returned 200, owner paths redirected to Access, and unauthenticated app and controller requests returned 403. The owner reported that both approved devices and the Mac's paired session survived deployment. A read-only SmartCast check found that the TV still displays the staging Conjure app 17.
2. The owner separately approved one live YouTube test. The Mac `cloud-poll` controller ran at a two-second interval; the owner pressed OK once on the Vizio's YouTube tile. The controller logged `Cloud command claimed: youtube` and `verified (app_confirmed)`. The claim establishes that the Worker accepted and queued a command, although the browser's raw HTTP 202 response was not captured independently. The controller's `verified` report means its authenticated `/app/current` check matched YouTube after SmartCast execution. A separate read-only post-test check returned namespace **5**, app ID **1**. The owner visually confirmed native YouTube opened. The controller was stopped with no further command processed.
3. The measured **enqueue-to-confirmed-TV-state latency was 2,136 ms** from the Durable Object's own timestamps. It includes queue wait, controller polling, SmartCast launch, and app-state readback. It does not measure the exact physical remote keypress-to-screen-pixel interval, which was not instrumented. No other native application was tested through the cloud bridge.

Production Horizon, production automation, Pico firmware, and the existing five SmartCast mappings remain untouched. No commit, merge, or push is part of this plan.

## Pico 2 W after a successful Mac cloud launch

The Pico 2 W is reported to run MicroPython v1.29.0 and to have connected to Wi-Fi and Cloudflare HTTPS. **Certificate validation has not been verified**, so HTTPS connectivity alone is not a credential-protection result. Before replacing the Mac, separately validate a plausible clock, CA trust, `CERT_REQUIRED`, SNI/hostname matching, and negative tests for wrong CA, wrong hostname, and expired certificates on the actual board. Separately establish a supported fail-closed trust method for the Vizio's SmartCast certificate before copying its auth token. Measure free heap and Wi-Fi recovery through repeated HTTPS and SmartCast calls. Only then implement a Pico-specific fixed-allowlist poller, mock-test it, provision distinct credentials with approval, and perform one controlled YouTube launch. Automatic Horizon startup and Home handling remain separate opt-in work. See [PICO2W_CONTROLLER_ASSESSMENT.md](PICO2W_CONTROLLER_ASSESSMENT.md).

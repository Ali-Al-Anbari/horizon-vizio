## Local protocol

The public Horizon page requests a ten-character, cryptographically random code. The Worker sets a five-minute `__Host-horizon_pending` cookie, with `Secure`, `HttpOnly`, `SameSite=Strict`, and `Path=/`. Only a SHA-256 hash of the pending secret and the code is stored in the one SQLite-backed Durable Object. The code appears on the TV and is entered by the owner at `/owner`; it never goes into a URL, localStorage, or logs. The owner page must be behind a **new, owner-only Cloudflare Access application**. The Worker independently validates the Access JWT signature, issuer, audience, expiry, and owner identity for every `/api/owner/*` operation. The owner reviews claimed browser details, verifies the matching code on the physical TV, and explicitly approves or rejects the exact pending request.

The TV polls `/api/pair/status` from the same origin, with the pending cookie. Approval lets that pending session receive a random `__Host-horizon_session` cookie. The session token is never returned to JavaScript; the Durable Object stores only its hash. The approval/code can be consumed once. If the one-time session response is lost, the TV must request a new code and the owner should revoke the orphaned approved device in `/owner`. The session lasts seven days, rotates on a subsequent session check after 24 hours, and has a 30-day absolute lifetime. Owner revocation invalidates it immediately for new requests. Active devices are capped at four; pairing starts are capped at five per source and 30 globally per ten minutes; owner code lookups are capped at 20 globally per five minutes. These limits are a small prototype policy; review Cloudflare WAF rate limits before wider exposure.

Browser write endpoints require an exact same-origin `Origin` and a custom action header. Launch requests accept only the existing five verified app identifiers, and the Durable Object checks the device session again atomically with queue insertion. Controller claim/result calls require a separate random bearer credential stored only in Cloudflare secrets and the Mac controller's protected local file. The controller's fixed allowlist and TV `/app/current` confirmation remain unchanged. Queued commands are canceled on device revocation. A command already claimed by the controller may already be reaching the TV and cannot be recalled; revocation blocks subsequent launches.

The queue retains its single active slot, 30-second queued expiry, 35-second processing expiry, 120-second result retention, and 12-second cooldown. A duplicate request from the **same device** for the same active app returns the existing command ID. Another device cannot read that command's status. The controller never retries a claimed command after an uncertain result. A healthy two-second Mac poll adds 0–2 seconds to claim latency, plus SmartCast launch and browser result polling (up to two seconds per status check). Offline controller work expires as `controller_offline` instead of silently succeeding.

## Isolated staging setup and next gate

1. A new hostname/path-based Cloudflare Access application protects `/owner`, `/owner.html`, and `/api/owner/*` for the owner's exact identity. Worker-wide Access remains off for public pairing routes. The Worker independently validates the Access JWT on owner API calls. Cloudflare documents [path-specific Access applications](https://developers.cloudflare.com/workers/configuration/cloudflare-access/) and [path wildcard behavior](https://developers.cloudflare.com/cloudflare-one/access-controls/policies/app-paths/).
2. The owner-approved staging deployments are complete. Their Worker name and SQLite Durable Object namespace differ from both production and the cookie-only probe. The current launch configuration retains the same pairing state, keeps the staging Access settings as Worker secrets, and uses a separate 256-bit `CONTROLLER_TOKEN` secret for outbound Mac polling. Only YouTube is enabled for launch in this staging phase. Never reuse the SmartCast pairing token as the cloud controller token.
3. Mac browser owner login, authenticated device-list API, code approval, first-party session creation, reload persistence, and owner device listing are verified by owner report. TV pairing and ordinary exit/relaunch persistence are also verified by owner report. A separate unauthenticated browser-profile test, live revocation test, and full TV reboot of the actual pairing session have not yet been performed. The queue and launch allowlist have local mock tests.
4. The separately approved YouTube cloud test succeeded: the controller claimed one command, observed `/app/current` namespace 5/app ID 1, and the owner visually confirmed native YouTube. The Mac poller was stopped after the test. The four other verified apps remain disabled in staging until a later approved phase.

The staging URL is `https://horizon-pairing-staging.ali-al-anbari.workers.dev/`. Owner Access and paired-device authorization are configured and verified. The existing production Worker and authentication probe remain separate.

## Pico 2 W gate

The purchased board is a Pico 2 W microcontroller, not a Linux Pi. The owner reports MicroPython v1.29.0, working Wi-Fi, and Cloudflare HTTPS connectivity. Certificate validation, reconnect behavior, repeated TLS heap use, and a fail-closed trust method for this TV's unusual SmartCast certificate remain unverified. The existing Pico draft uses `CERT_OPTIONAL` plus an unverified callback; MicroPython documents that `CERT_OPTIONAL` does not perform built-in validation on mbedTLS. The Mac controller also currently uses an unverified TLS context for the TV, so that code cannot be copied as a secure Pico baseline. See [PICO2W_CONTROLLER_ASSESSMENT.md](PICO2W_CONTROLLER_ASSESSMENT.md).

No Pico flash, credential copy, controller deployment, automatic Horizon startup, or Home-screen interception is authorized by the local prototype.
